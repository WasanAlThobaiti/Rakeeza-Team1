# Service indicators and proposed targets

Team: Team 1

Use case: Streaming chat service that generates responses for users through a vLLM-hosted language model.

Service measured: Qwen/Qwen2.5-1.5B-Instruct-AWQ, chat completion endpoint, namespace team.

Workload: Artificial chat requests generated by traffic.py; one caller for 60 seconds, 30-second pause, then up to four callers for 60 seconds, with responses capped at 64 output tokens.

Measurement period: 2026-09-13T10:16:42+00:00 to 2026-09-13T10:19:43+00:00 UTC

Instrumentation gaps: Output quality and user-perceived correctness are not measured by the current Prometheus metrics.

## SLI 1

Indicator: p95 time to first token.

Panel: p95 Time to First Token

Unit: seconds

Target: p95 TTFT <= 0.10 seconds.

Window: 5 minutes

Observed: 0.0390 seconds p95 TTFT during the 120-request traffic.py workload from 2026-09-13T10:16:42+00:00 to 2026-09-13T10:19:43+00:00 UTC.

Evidence: Grafana Team service dashboard using vllm:time_to_first_token_seconds_bucket, measured during the traffic.py run from 2026-09-13T10:16:42+00:00 to 2026-09-13T10:19:43+00:00 UTC.

Why it fits: Time to first token directly affects how quickly a user sees the service begin responding, so lower TTFT improves perceived responsiveness.

Limitations: The measurement comes from a short synthetic lab workload with a limited request count. The 0.10-second target is provisional and should be retested under longer-running and more realistic workloads.

## SLI 2

Indicator: Completed requests per minute.

Panel: Completed requests/min

Unit: requests/min

Target: >= 20 requests/min under the lab workload.

Window: 5 minutes

Observed: approximately 22.74 requests/min during the recorded measurement, with later traffic reaching approximately 25.3 requests/min.

Evidence: Grafana Team service dashboard using vllm:request_success_total with finished_reason=~"stop|length", measured during the traffic.py run from 2026-09-13T10:16:42+00:00 to 2026-09-13T10:19:43+00:00 UTC.

Why it fits: Completed requests per minute measures whether the service can sustain useful request throughput while serving users.

Limitations: This measures completed requests but does not prove response correctness or quality. Results depend on request shape, concurrency and output length, and should be retested with longer and more realistic workloads.
